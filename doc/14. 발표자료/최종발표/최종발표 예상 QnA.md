# AIpass 최종 발표 예상 QnA

## 시스템 개요

**Q. 이 시스템이 기존 무인 단속 시스템과 다른 점이 무엇인가요?**
> 기존 단속 시스템은 루프 감지기나 고정식 레이더로 단일 위반만 감지합니다. AIpass는 CCTV 영상 하나로 과속·실선침범·혼잡도 분석을 동시에 처리하며, 여기에 교통 장비 고장을 사전에 예측하는 예지보전 기능까지 하나의 플랫폼에 통합한 것이 차별점입니다.

**Q. 시연 환경을 4대 PC로 분산한 이유가 무엇인가요?**
> YOLO 추론과 PaddleOCR은 CPU/GPU 연산이 무거워서 하나의 PC에 올리면 스트리밍 지연이 발생합니다. 과속 감지(112), 실선침범 감지(59), 예지보전(29), 프론트+백엔드(173)를 역할별로 분리해 각 기능의 실시간 성능을 확보했습니다.

## AI / 과속 감지

**Q. 카메라 픽셀 좌표로 어떻게 실제 속도를 계산하나요?**
> 호모그래피(Homography) 변환을 사용합니다. 영상 내 4개 기준점을 실세계 좌표(10m × 30m 구간)에 대응시키는 변환 행렬을 미리 계산해 두고, 차량의 타이어 접지면 픽셀 좌표를 실제 미터 좌표로 변환합니다. 이후 이동 거리 ÷ 경과 시간 × 3.6으로 km/h를 산출합니다.

**Q. 속도가 튀거나 노이즈가 심하면 오탐이 생기지 않나요?**
> EMA(지수이동평균, alpha=0.3)로 스무딩하고, 70km/h를 5프레임 연속 초과해야만 위반으로 확정합니다. 단일 프레임 이상치는 필터링되며, 동일 track_id에 `is_reported=True`를 설정해 중복 단속도 방지합니다.

**Q. ByteTrack을 왜 사용했나요?**
> ByteTrack은 신뢰도가 낮은 박스도 2차 매칭에 활용해 차량이 잠시 가려져도 동일 ID를 유지합니다. 속도를 여러 프레임에 걸쳐 누적 계산하는 구조에서 ID가 끊기면 측정이 초기화되므로, 안정적 트래킹이 필수입니다.

## 번호판 OCR

**Q. 번호판 인식 정확도가 어느 정도인가요?**
> PaddleOCR 4단계 폴백 파이프라인을 적용해 내부 테스트 기준 약 85%의 인식률을 달성했습니다. 다만 실제 RTSP CCTV 영상은 해상도가 낮아 현장 적용에는 한계가 있으며, 시연에서는 사전 수집한 차량 이미지를 대체 입력으로 사용합니다.

**Q. 4단계 폴백이란 구체적으로 무엇인가요?**
> 원본 크롭 → CLAHE 밝기 보정 → HSV 컨투어 기반 번호판 영역 재탐지 → 슬라이딩 윈도우 순으로 시도하며, 각 단계에서 신뢰도 0.6 이상, 정규식(`12가3456` 형식) 검증을 통과해야 최종 결과로 채택합니다.

**Q. 야간이나 악천후에서도 작동하나요?**
> CLAHE(Contrast Limited Adaptive Histogram Equalization)로 야간 저조도 영상의 대비를 보정하는 단계를 포함하고 있습니다. 강우·안개 환경은 현재 별도 전처리가 없어 인식률 저하가 예상되며, 이는 개선 계획에 포함되어 있습니다.

## 예지보전

**Q. 예지보전에서 XGBoost를 선택한 이유는 무엇인가요?**
> 교통 장비 센서 데이터는 수십 개 특성을 가진 정형 데이터입니다. 정형 데이터에서 XGBoost는 딥러닝 대비 학습 속도가 빠르고, 특성 중요도를 직접 해석할 수 있어 장비 어느 센서가 RUL(잔여 수명)에 영향을 미치는지 설명 가능한 모델을 만들 수 있습니다.

**Q. RUL 예측값은 어떻게 계산되나요?**
> ML 모델이 마지막으로 예측한 RUL 값을 DB에 저장하고, 현재 표시값은 `저장된 RUL − 경과 일수`로 계산합니다. 주변 기온은 기상청 KMA API에서 수집해 `ExpectedTemp = ambient_temp + 장비 평균 발열값`으로 보정합니다.

**Q. 실제 장비 데이터 없이 예지보전이 가능한가요?**
> 현재는 12대 센서를 시뮬레이션하는 `simulator.py`로 데이터를 생성합니다. 실제 장비에 IoT 센서를 부착해 동일한 API 포맷으로 데이터를 수집하면 시뮬레이터를 실제 데이터로 교체할 수 있도록 파이프라인을 설계했습니다.

## 아키텍처 / 기술 설계

**Q. FastAPI와 Spring Boot를 왜 분리했나요?**
> AI 추론은 Python 생태계(ultralytics, PaddleOCR, OpenCV)에 의존하고, 비즈니스 로직은 Spring의 트랜잭션·세션 관리가 적합합니다. 역할별 언어 최적화와 독립 배포를 위해 분리했으며, FastAPI → Spring Boot는 Webhook으로 연동합니다.

**Q. Webhook 전송 실패 시 데이터 유실은 없나요?**
> DLQ(Dead Letter Queue) 패턴을 적용했습니다. 전송 실패 시 `fallback_queue.jsonl`에 저장하고, 5분마다 재시도합니다. `asyncio.Lock`으로 파일 I/O 원자성을 보장해 재시도 중 신규 실패 데이터를 덮어쓰지 않습니다.

**Q. 세션 기반 인증을 선택한 이유는 무엇인가요?**
> 내부 관제 시스템으로 외부 API 노출이 없습니다. JWT는 토큰 탈취 시 만료 전까지 무효화가 불가능하지만, HttpSession 방식은 서버에서 즉시 세션을 삭제해 강제 로그아웃이 가능합니다. 관제 시스템의 보안 제어 요구에 더 적합합니다.

**Q. MJPEG 스트리밍이 끊기는 문제는 없나요?**
> 영상 수집(Process A) - AI 추론(Process B) - 스트리밍(RenderThread)을 분리하고, 큐(`mjpeg_queue`, `meta_queue`)로 연결했습니다. 추론이 느려지면 큐가 완충 역할을 해 스트림이 직접 영향받지 않으며, `QUEUE_MAXSIZE=1000`으로 OOM을 방지합니다.

## 한계 및 개선 방향

**Q. 실제 상용화 시 가장 큰 문제점은 무엇인가요?**
> 세 가지입니다. ① 번호판 OCR은 고해상도 카메라(최소 2MP 이상)가 전제조건입니다. ② 호모그래피 보정값은 카메라 설치 위치·각도마다 현장 측정이 필요합니다. ③ 예지보전 모델은 실제 장비 고장 이력 데이터로 재학습이 필요합니다.

**Q. 개인정보(번호판) 처리는 어떻게 하나요?**
> 현재는 위반 차량 번호판만 저장합니다. 실제 운영 시에는 「도로교통법」 및 「개인정보 보호법」에 따라 위반 데이터 보존 기한 설정, 접근 권한 관리, 암호화 저장이 필요하며, 이는 운영 정책 수립 단계에서 반영해야 합니다.

**Q. 교통신호 제어가 실제로 신호를 바꿀 수 있나요?**
> 현재 TrafficView는 더미 데이터 기반 UI입니다. 실제 신호 제어는 교통 신호 제어기(TSC)와 표준 프로토콜(NTCIP) 연동이 필요하며, 관할 기관 승인 절차가 있어 프로토타입 범위에서는 UI 시뮬레이션으로 구현했습니다.

## 팀 / 프로세스

**Q. 역할 분담은 어떻게 했나요?**
> 배영환(PM·FastAPI AI 서버·단속·신호 제어), 김소연(기획·DB ERD·화면 설계·테스트), 하재영(대시보드·예지보전 AI·CCTV)으로 분담했습니다. 서버 간 인터페이스(Webhook 스펙, API 명세)를 먼저 합의한 후 병렬로 개발했습니다.

**Q. 가장 어려웠던 기술적 문제는 무엇이었나요?**
> MJPEG 스트리밍과 AI 추론을 같은 프로세스에서 처리하면 추론 부하가 커질 때 스트림이 멈추는 문제가 있었습니다. 프로세스를 3개(영상 수집 / AI 추론 / 렌더링)로 분리하고 SharedMemory + Queue로 연결해 해결했습니다.
